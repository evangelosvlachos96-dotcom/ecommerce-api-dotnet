An order goes Submitted, Paid, Dispatched. The code makes sure of it.

A .NET 6 Web API for a small shop. Users sign in with a JWT, the product catalogue is pulled from an external source on a daily schedule, payment runs through Stripe Checkout, and a PDF invoice is generated and e-mailed the moment an order is paid. One process, EF Core, SQL Server.

Start in four steps

Needs the .NET 6 SDK, SQL Server (LocalDB is enough) and the EF Core CLI. Stripe test keys and an SMTP account only if you want payment and e-mail to work end to end.

1 · Configure

In EcommerceApp/: cp appsettings.Example.json appsettings.json. Real settings are git-ignored.

2 · Fill in the keys

ConnectionStrings:EcommerceDB, JwtSettings:Key (32+ chars), Stripe:SecretKey, and the SmtpSettings block. Or use dotnet user-secrets set.

3 · Create the database

dotnet ef database update --context EcommerceContext applies the code-first migration.

4 · Run

dotnet run, then open https://localhost:7063/swagger. Log in via POST /api/users/login and paste the bearer token into Authorize.

How it works

A layered monolith: controller → service → repository → EF Core. The interesting parts sit inside the services and the Order entity.

Order is a state machine

Private setters, a factory constructor, and three guarded transitions: MarkPaid only from Submitted, StoreInvoice only once and only when Paid, MarkDispatched only when Paid and an invoice exists. Callers cannot set Status directly.

Stripe Checkout

The payment service builds a Checkout Session from the order's line items and returns the hosted URL. Stripe redirects back to checkout-confirm, which marks the order paid and kicks off the invoice.

PDF invoice by e-mail

PdfSharpCore renders the invoice server-side. MailKit sends it as an attachment over SMTP. The base64 PDF is stored on the order, so it can be downloaded or re-sent later.

Catalogue sync on a schedule

A Quartz job replaces the Products table from fakestoreapi.com inside a transaction every day at noon (0 0 12 * * ?). Admins can fire the same job on demand with GET /api/products/sync.

JWT with a custom model binder

[FromJwtUserId] binds the userid claim straight into action parameters, so a client cannot spoof it in the body. A Swagger filter hides that parameter from the generated docs. Admin actions require an admin claim.

One response envelope

Services return a result object instead of throwing for expected failures. Controllers wrap it in APIResult<T> with Status, Data and Error, so happy and sad paths look the same on the wire.

The API

Everything under api/[controller]. Only register and login are anonymous.

Data model
  1. Users — GUID key, first and last name, e-mail, password, role (Basic or Admin)
  2. Products — id from the external catalogue, title, price, category, image, and an owned Rating value object stored as two columns
  3. Orders — GUID key, owning user id, total, status, nullable base64 invoice, timestamps
  4. OrderProducts — the many-to-many join table EF generates for Order.Products

The repository's architecture notes explain why it is layered rather than Clean or hexagonal, and list what would need hardening before production: password hashing instead of reversible encryption, Stripe webhooks instead of trusting the redirect, tests, indexes, tighter CORS. The data model notes cover the schema decisions.
